# Smart Traffic Congestion Prediction using IoT Sensors and AI

Prepared by Ali Raza | Version 1.0

> **Read first — simulated data only:** This project uses **no real IoT
> hardware, no real city traffic data and no real sensor feeds**. Every
> reading is generated by a simulator with rush-hour, weather and event
> patterns. The prediction model is trained and evaluated **only on
> synthetic data**. This is an **educational demo, not a traffic-control
> system** — it never controls real traffic signals. Signal suggestions are
> **advisory only**. Intersection and city names are fictional.

## 1. Project Overview

Smart Traffic Congestion Prediction is a demo system that shows how IoT
sensors, a database, a machine-learning model and a web dashboard could work
together for city traffic. Simulated sensors at six fictional intersections
report vehicle counts, average speed, occupancy and queue length every
5 minutes. A Random Forest model predicts the congestion level and vehicle
count for the next 15, 30 or 60 minutes, and the dashboard shows current
congestion, predictions, advisory signal-timing suggestions, alerts and
reports.

## 2. Problem Statement

Traffic congestion wastes time, fuel and road capacity, and it is hard to
plan for because it changes by time of day, weather and events. Real
traffic systems need sensor data and forecasting, but building and testing
them on live roads is expensive and risky. A simulated version lets a
student or developer show the full pipeline — sensing, storage, prediction,
visualisation and advisory control — safely, with honest limits.

## 3. Objectives

- Simulate IoT sensor readings for several intersections with realistic
  daily patterns.
- Predict congestion level (Low / Moderate / High / Severe) and vehicle
  count for 15, 30 and 60 minutes ahead.
- Show a live dashboard with KPIs, charts, intersection detail and alerts.
- Suggest green-time adjustments as **advisory only** suggestions.
- Raise alerts for high congestion and offline sensors (in-app only).
- Provide hourly/daily reports and CSV export.
- State clearly, everywhere, that the data is simulated.

## 4. Scope

In scope: sensor simulation, storage, ML training/evaluation on synthetic
data, prediction API, dashboard, advisory signals, alerts, reports, support
tickets, settings.

Out of scope: real IoT hardware, real traffic feeds, real signal control,
real SMS/email alerts, multi-city deployment, mobile app.

## 5. IoT Sensor Design

Each fictional intersection has one main sensor (vehicle count + speed +
occupancy) and, at one intersection, a second queue sensor. Sensors report
every 5 minutes:

| Field | Meaning |
| --- | --- |
| `vehicle_count` | Vehicles counted in the 5-minute window (simulated) |
| `avg_speed_kmh` | Average speed, falls as occupancy rises (simulated) |
| `occupancy_percent` | Share of road capacity used (simulated) |
| `queue_length` | Vehicles waiting, derived from occupancy (simulated) |
| `weather` | clear / cloudy / rain (simulated pattern) |
| `event` | Local event flag, e.g. Friday evening near Main Rd (simulated) |

Sensor health is tracked: `online`, `degraded` (low battery) and `offline`.
One sensor is deliberately offline in the demo so the offline-alert path
can be exercised. No real sensor is ever contacted.

Congestion levels from occupancy: Low < 40%, Moderate < 65%, High < 85%,
Severe ≥ 85%.

## 6. Machine Learning Methodology

1. **Generate** 14 days of synthetic 5-minute readings per intersection
   (seeded, reproducible) with morning/evening rush peaks, weekend
   reduction, rain and event multipliers, plus noise.
2. **Features:** time-of-day (sine/cosine), day of week, weekend flag,
   rush-hour flag, weather code, event flag, and the last three counts plus
   a 30-minute rolling mean.
3. **Targets:** the congestion level and vehicle count 15 minutes ahead.
   For 30/60 minutes the 15-minute model is rolled forward, feeding its
   own predicted count back as the newest lag (documented rollout).
4. **Models:** Random Forest classifier (congestion level) and Random
   Forest regressor (vehicle count), trained on a chronological 80/20
   split. Metrics (accuracy, confusion matrix, MAE, RMSE) are reported in
   `docs/evaluation_report.json` and on the Reports page — **synthetic
   data only**.
5. **No shipped model file:** `ml/train.py` can save a local model under
   `ml/artifacts/` (gitignored). The API retrains in memory at startup
   from simulated data, so a fresh setup never needs a downloaded artifact
   and no file is presented as a "trained real model".

If scikit-learn is not installed, training raises a clear error instead of
returning a fake prediction.

## 7. Features

- **Dashboard:** KPIs, recent-counts line chart (SVG), occupancy bar
  chart (SVG), current congestion table.
- **Intersections:** fictional intersection list with capacity and latest
  simulated reading; sensor list with status and battery.
- **Predictions:** pick an intersection and horizon (15/30/60), get a
  predicted level and count, with the weather/event used.
- **Signals:** advisory green-time suggestions (base 30 s, −5 to +15 s by
  level, clamped to 20–55 s), labelled advisory only on every row and
  in the API response.
- **Alerts:** congestion and sensor-offline alerts, acknowledge in-app.
  No SMS/email is sent.
- **Reports:** total readings, readings by level, average count by
  intersection, classifier accuracy / MAE / RMSE on synthetic data,
  confusion matrix, CSV export.
- **Support & Help:** guides, FAQs, ticket form (Open / In Progress /
  Resolved), contact card from Settings with empty defaults — no phone or
  email is invented.

## 9. System Architecture

```
Simulated sensors (ml/simulator.py)
        │  5-minute readings, seeded
        ▼
SQLite store (api/store.py) ──► FastAPI (api/main.py)
        │                            │  /api/congestion, /api/predict,
        │                            │  /api/signals, /api/alerts, /api/reports
        ▼                            ▼
ML training (ml/model.py)      React dashboard (web/)
  Random Forest, synthetic         Dashboard / Intersections /
  data only                        Predictions / Signals / Alerts /
                                   Reports / Support
```

Prediction flow: choose intersection + horizon → API takes the latest
simulated readings → features → classifier + regressor → level + count,
with a note that the model was trained on simulated data only.

## 10. API Endpoints

| Method | Endpoint | Purpose |
| --- | --- | --- |
| GET | `/health` | Service status, states simulated-only |
| GET | `/api/intersections` | Intersections with latest simulated reading |
| GET | `/api/sensors` | Simulated sensor list and health |
| GET | `/api/readings?intersection_id=&limit=` | Recent simulated readings |
| GET | `/api/congestion` | Current simulated congestion per intersection |
| GET/POST | `/api/predict` | Predict level + count (15/30/60 min) |
| GET | `/api/signals` | Advisory green-time suggestions only |
| GET | `/api/alerts` | Alert list (simulated) |
| POST | `/api/alerts/{id}/acknowledge` | Acknowledge an alert |
| GET | `/api/reports` | Summary + model metrics (synthetic) |
| GET | `/api/reports/export` | CSV export of simulated readings |
| GET | `/api/model-info` | Training source + metrics |
| GET/POST/PATCH | `/api/support/tickets` | Support tickets |
| GET/PUT | `/api/settings` | City/contact/threshold settings |

No authentication is used in this demo; the API is intended to run locally.
Do not expose it publicly without adding authentication.

## 11. Database / Schema

SQLite tables (local file `data/traffic.sqlite`, gitignored):

- `readings` — intersection_id, sensor_id, timestamp, vehicle_count,
  avg_speed_kmh, occupancy_percent, queue_length, weather, event,
  congestion. Unique on (intersection_id, timestamp).
- `alerts` — intersection_id, type, message, severity, created_at,
  acknowledged.
- `support_tickets` — name, subject, message, priority, status, reply,
  created_at.
- `settings` — key/value (city name, contact email/phone, alert
  threshold, base green time).

## 12. User Interface Pages

Dashboard, Intersections, Predictions, Signals (Advisory), Alerts, Reports,
Support & Help. Every results page carries the simulated-data notice, and
the Signals page carries the advisory-only warning.

## 13. Privacy and Ethics

- No real people, vehicles or locations are identified; all names and
  data are fictional/simulated.
- No licence plates, camera images or personal data are collected.
- A real deployment would need data-protection review, secure sensor
  communication and human oversight of any signal change. This demo
  deliberately does none of that, and says so.

## 14. Testing Plan

- Simulator: thresholds, rush-hour vs night pattern, history length,
  determinism with a fixed seed.
- Model: metrics are synthetic-only, valid horizons accepted, invalid
  horizon rejected.
- API: health, congestion, predict (valid / unknown intersection / bad
  horizon), advisory-only signals, reports + CSV export, ticket flow.
- UI: frontend build, browser screenshots of every page with the API
  running.

## 15. Setup Guide

Backend (Python 3.10+):

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python -m ml.evaluate        # retrains on simulated data, writes docs/evaluation_report.json
uvicorn api.main:app --reload --port 8000
```

Frontend:

```bash
cd web
npm install
npm run dev          # http://localhost:5173 — API at http://localhost:8000
npm run build        # production build
```

Tests:

```bash
pytest -q
```

## 16. Deployment

- API: any Python host (Render/Railway/VPS) with `uvicorn`; set
  `TRAFFIC_DB` to a persistent path if needed.
- Frontend: Vercel/Netlify static hosting, with `VITE_API_URL` pointing
  at the API. Live deployment was not verified in this build.
- For a real city this architecture would need real sensors, a message
  queue, a production database and human-reviewed signal control — all
  out of scope for this demo.

## 17. Limitations

- All data is simulated; patterns are simplified and cannot describe
  real traffic.
- The model has never seen real traffic and must not be used for real
  decisions.
- Signal suggestions are advisory only and untested against real
  signal hardware.
- No authentication, no real alerts delivery, no live database or
  deployment verified.
- One sensor is deliberately offline in the demo data.

## 18. Future Improvements

- Connect real (authorised) sensor feeds behind an authenticated
  ingestion service.
- Time-series models (e.g. LSTM) and per-intersection calibration.
- Real signal-controller integration with human approval and audit log.
- Map view with real (licensed) map tiles, multi-city support, mobile app.
- Alert delivery via email/SMS with user consent, and role-based access.

## 19. Conclusion

Smart Traffic Congestion Prediction shows the complete pipeline — IoT
sensor simulation, storage, machine-learning forecasting, a dashboard,
advisory signal suggestions, alerts and reports — with the honesty limits
stated throughout: simulated data only, synthetic model, advisory signals
only. That makes it a strong portfolio project for AI/ML and full-stack
interviews, without ever claiming to control real traffic.

## Demo Notes (honest)

- Simulated sensor data only; no real IoT hardware or real city data.
- Model trained/evaluated on synthetic data; see
  `docs/evaluation_report.json`.
- Signal suggestions are advisory only.
- SQLite locally; live Postgres/deployment not verified.
- Screenshots in `docs/screenshots/` are local only (binary files cannot
  be pushed with the text-only GitHub API); the folder on GitHub contains
  only `.gitkeep` until the PNGs are uploaded manually.
